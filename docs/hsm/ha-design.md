# HSM 优化方案的 HA 约束与设计

状态：分阶段实施，尚未完成端到端 HA 验收。P1 已增加普通日志自身回执、本节点提交及 originating term 校验，见 [提交回执改造](commit-receipts.md)；其余目标按本文逐项实施。它是 [性能优化方案](optimization-plan.md) 的前置约束，从 P0/P1 起执行。

## 1. 当前基础、缺口和目标范围

已有基础包括三个 Master 的 Raft 权威域、持久任务/原始结果、controller epoch 条件接管、稳定源视图、私有恢复、Worker Seal 和提交后 GC。已验证进程重启、去掉旧 leader 后恢复，以及百万 namespace 的 checkpoint 恢复。

这些不能合并为“端到端 HA 已完成”：当前 PVE 虚拟机都在同一物理宿主机；控制器和 LocalArchive 在同一节点；LocalArchive 只有本地文件 fsync；控制器 Running 接管仍需显式提升 epoch；Recall 私有布局是单 Worker、单副本，尚未纳入普通块修复。百万 namespace 测试的三个 Master/一 Worker 在同一 fixture 进程，也不是多物理故障域测试。

目标覆盖：单 Master/Worker/控制器/执行器进程或节点故障，网络分区、长时间暂停后恢复，以及提交/回执之间的崩溃。元数据多数派、所需数据副本和归档后端仍可用时，系统应自动接管；丢失多数派时不接受新的权威变更。超出副本容错范围的相关故障、整站灾难恢复另行设计。

目标 RPO：在满足同步持久化、故障域和副本写确认约束时，已确认的元数据操作及所声明持久的文件/归档版本不因一个目标节点故障而丢失。元数据 Raft 的多数派并不能替代文件 payload 和归档目录的冗余。

## 2. 分层责任与部署目标

| 层 | HA 责任 | 需要持久保留的事实 |
|---|---|---|
| 存储侧 Master | 选主、命令顺序、条件执行、请求去重、租约/布局发布、任务与 GC 恢复 | 原生 namespace、HSM 记录/索引、结果与请求身份、授权、任务、reservation、outbox，在同一提交恢复点 |
| 存储侧 Worker | 在线数据副本、恢复布局的耐故障能力、授权校验与旧写入隔离、已提交 GC 重试 | payload、allocation/Seal/删除状态，以及必要的 fencing 状态 |
| 策略层 | 从源端恢复规则、周期、游标和预算；筛选后重新校验 | policy revision、调度/游标检查点、active intent、预算账本；不放在某个扫描进程的内存作为唯一事实 |
| hsm-rs | 首版双实例主备、资格续约、自动接管与逐动作对账 | Curvine 中的 controller owner/epoch/lease、任务 claim 和结果；无外部全量 namespace 镜像 |
| data-mover | 可重试搬运、尝试隔离、传输证据；执行节点失效可重做 | 逻辑 job/attempt 标识及权威源/目标绑定；spool 可以是可丢弃的本地中间数据 |
| ArchiveBackend / EE 等后端 | 归档对象与目录/回执的持久性、可接管访问、原始提交查询和隔离旧写入 | 数据及精确 ArchiveKey 对应的不可变提交事实；这不是源 namespace 镜像 |
| SDK/FUSE | 稳定请求身份、发现新 leader、授权续期、能力缓存更新、透明重试 | 必要的 session/sequence 或可恢复逻辑操作标识；不根据超时自行判定权威动作失败 |

部署目标是三个 Master 分布在至少三个独立物理/存储故障域；Worker 的数据副本也跨所需故障域，hsm-rs 两实例分置不同节点。多份 journal 在同一个宿主机或同一个底层盘上仍共享故障点。所有 Worker 继续以各自本地盘组成 Curvine，无需引入 UFS；归档后端的冗余独立设计。

## 3. 不同身份不能混用

| 身份 | 含义及变化条件 |
|---|---|
| cluster/namespace incarnation | 区分整个存储历史；普通换主不改变 |
| Raft term 与日志位置 | 证明某个命令处于哪一任期和提交位置；不是逻辑请求 ID |
| client session + request sequence | 普通请求跨重连/超时的去重身份；相同身份必须绑定同一请求指纹 |
| operation_id | HSM 逻辑工作流身份；换主或控制器接管后保持 |
| controller_epoch | 外部控制者资格；接管通过 Curvine 条件提交推进，不因每次 Master 换主自动增加 |
| attempt/claim epoch 或 token | 某次执行尝试的资格；新尝试不能覆盖旧尝试已封存的对象 |
| generation、layout/read authorization epoch | 内容版本、布局和读取授权的隔离；与 Raft term、controller epoch 分别处理 |

当前原生协议限制 `attempt_epoch=1`，现有 Worker 写入主要检查 allocation token、Seal/删除状态；不能把上表的目标资格体系当作已经全部由 Worker 校验。需要新增的 attempt/授权 fencing 必须在相应路径一起实现。

## 4. 微批提交在换主时的语义

稳定幂等键采用 `namespace incarnation + client session + request sequence`，请求指纹防止同一身份换参数。HSM 工作流仍以稳定 operation_id/动作步骤匹配原始结果。**batch ID、内存 ticket、TCP request ID 均不能作为唯一恢复依据。**

| 故障发生时点 | 接管后处理 |
|---|---|
| 仅在旧 leader 的内存队列中 | 未确认请求由客户端携相同逻辑身份重试；新 leader 不依赖复制旧内存队列 |
| 已提议但未提交，尾部可能被覆盖 | 返回状态不确定并在新 leader 对账；不能凭旧 index 判断成功 |
| 已提交、旧进程尚未 apply/响应 | 新 leader 应用日志并恢复去重结果；重试返回原始结果 |
| 已 apply、回执丢失 | 查询匹配请求的已提交结果，不能重新执行 Release/发布 |
| 批内命令有条件失败 | 各命令拥有独立已提交结果；后续命令按顺序观察前一命令结果 |

去重结果的保留期不随选举任期结束而清空。过期清理前需持久保存可拒绝旧请求的 session/sequence 下限或等价 tombstone，不能将“结果已清理”解释为可再次执行。

去重绑定/结果与业务状态在同一权威提交序列中确定，确认条件为请求匹配、已提交、相关状态已在服务节点应用。只把普通 journal 的入队回执改名为 committed receipt 不满足要求。

旧 leader 一旦失去资格，就停止接收新权威命令和发放新授权。未确定命运的 waiter 返回可对账的不确定结果；取消 waiter 不撤销已提交命令。**已经有提交证明且匹配请求的历史成功结果，可以跨任期返回**；应禁止的是旧 leader 把本地 speculative 结果当成成功，或据此继续产生新的未授权效果。

新 leader 先验证任期/多数派资格，恢复一致 checkpoint 并应用必要日志，清除或重建未提交投影，再开放提交队列。HSM 的 CAS 不能读到未提交的普通修改。P1 保留现有 gate 的过渡版本也必须检查自身日志回执的任期及本地应用位置。

微批只改变持久化摊销，不改变单命令确认保证；队列设置条数/字节/等待上限。分区期间不会为保持吞吐而无限接收请求；恢复时限流重试与对账，前台/Recall 保留配额，扫描和 GC 保留最低进度。

## 5. Master 角色切换与冷启动分别处理

目标角色流程：

```text
Follower → 取得 leader 资格 → 核对 committed/apply 水位及恢复状态
         → Serving → 失去资格 → 停止新提交/授权 → Follower 或恢复
```

正常角色切换使用已追齐 follower 的状态，不重新遍历百万目录，也不因为选主再清空 HSM 投影。进程冷启动需要的有界清理/checkpoint/tail 恢复与单纯角色切换分开计时。

checkpoint 对齐 native inode、HSM 状态/索引、请求去重、任务、租约、预算和 GC 与同一个 applied index。恢复期间不开放可能执行 Release 的入口。旧磁盘或旧 checkpoint 重新加入必须从健康多数派追齐，不能靠旧目录存在就独立恢复服务。

Master 换主不自动重做所有 HSM 工作流。controller_epoch 与任务 claim 仍成立时，控制器刷新 leader 路由后继续查询/提交；无需仅因元数据换主就重传全部文件。

## 6. 读取租约与 Release 的 HA 约束

第一阶段继续持久化 reader/session、generation、访问观察和有效期。新 leader 从提交历史恢复读取保护，而不是把本机 readers 内存为空视为“无读者”。合批 close/renew 仍保留每个会话的单调序号及幂等结果，延迟到达的 close 不能删除一个更新授权。

租约有效期不能仅通过不同节点的裸墙上时间比较来判断。实施前必须定义最大授权时长、允许的时钟误差/跳变处理及重启恢复规则。无法证明旧授权已经失效时，要阻止破坏性释放/GC；可通过已确认的 Worker fencing，或按明确最大授权时长和安全余量进行保守等待。授权的截止时间不能因为回复迟到而从客户端收包时重新起算；已经过期的响应需重新授权。具体时钟方案未完成前，不开启无日志 delegation。

高级 delegation 方案需要可恢复的 `Draining/Revoking → 可释放` 流程：

1. 将阻止新授权的状态及授权 epoch 条件提交。
2. 撤销旧授权，并在相关 Worker 上安装 fencing；完成确认或满足有界到期证明。
3. 新 leader 核对仍有效的读保护、内容/布局版本和归档依据。
4. 提交 Offline 与 GC outbox，之后再物理清理。

Master 换主本身不证明客户端已经停止读取。多数派丢失时不再授予新的权威租约；已有读能否继续取决于仍有效且被 Worker 校验的授权协议，不能预先承诺分区侧持续读。临时无法证明安全时可以推迟后台 Release，同时保持健康多数派上的恢复与正常服务能力。

## 7. hsm-rs 自动接管与执行器恢复

首版先做两个控制器主备，避免在同一个 namespace epoch 机制下直接叠加任意多活。Curvine 增加 owner/lease 与现有 controller_epoch 的原子续约/条件接管；不需要为选主另建一份文件数据库。超时只是触发接管检查，新资格必须经多数派提交。

备用控制器的接管顺序：

1. 经 Curvine 条件提交取得新 epoch，旧控制者的权威修改被拒绝；实现有界租约的时钟与失联处理。
2. 分页恢复规则及 Ready/Running 工作索引、未完成 seal/GC 和预算；避免扫描全 namespace 或全部终态历史。
3. 对 Running 任务先查存储原始 outcome、后端 ArchiveKey/封存回执和私有恢复布局；已经完成的效果直接对账完成。
4. 仅对没有确证完成的阶段重做或新建隔离的执行尝试，确认结果后才推进状态。

源端 epoch 递增不能自动撤销已经交给旧执行器的所有字节写权限。目标布局/对象应按尝试隔离，Seal、删除与 backend finalize 也校验资格或使用不可变条件提交。旧执行器即使从 SIGSTOP/网络隔离恢复，也不能覆盖新尝试、发布布局或删除新数据。不得只依赖“已通知旧进程退出”。

data-mover 的本地 spool 可丢弃；执行器节点故障后可以重新搬运，源视图/目标绑定与结果由权威端对账。允许物理复制重做，不允许同一逻辑动作重复发布或错误释放。传输证据不替代 ArchiveBackend 的持久封存回执。原逻辑 operation_id 保持，新 attempt 是否能复用已封存内容必须根据身份、长度和摘要确认。

当前 CLI 在启动时取得 epoch，并直接打开独占 LocalArchive root；它不是现成的跨节点主备守护进程。自动续约、接管循环、backend 所有权及尝试隔离需要实际实现与联测。

## 8. 在线数据、Recall 布局和归档后端

### 普通在线数据

HA 验收须明确 replicas、写入确认需要的副本数 W、每份确认的落盘语义、故障域、降级写入策略以及修复策略。验收“已确认版本允许丢一 Worker 节点”前，必须验证写成功时已有足够跨节点持久副本；不能仅凭 replicas 配置值推导 RPO。

Worker 掉线后由存储侧更新可用布局并触发修复，元数据选主不会复制丢失的 payload。若失去全部在线副本而仍有健康归档，应合并为同版本恢复任务；无健康副本且无归档时不得报告数据可用。

### Recall 后的数据

优先评估恢复至普通块副本体系：隐藏准备目标、写足所需副本、Seal/摘要验证，再条件发布至原 inode。也可先给私有布局补多副本、可接管读路由及修复，但这些都不是目前已实现能力。

若暂时把单副本 Recall 数据定义为可丢弃缓存，必须实现“已发布布局丢失 → 存储重校验故障/版本/锚点 → 一次恢复任务 → 新布局发布”的自动修复。不能仅因归档还在，就认为当前单副本布局故障后读请求已经能自动恢复；单次网络超时也不能直接判定数据永久丢失。

### 归档后端

LocalArchive 的数据和 catalog/receipt 都是本地单节点文件。增加另一个 controller 不会复制这些数据，其独占 root 锁也不能直接变成跨节点主备访问机制。

节点级 HA 至少需要一个具有独立数据/目录冗余和可接管访问端点的后端；或者将同版本归档到多个独立故障域，并让 Release 条件验证所要求的多份已封存锚点。后者需要新增多归档耐久性策略，当前单 backend 策略不能被描述为自动满足它。

归档数据、精确对象身份和封存回执必须一起满足耐故障要求，spool 副本不计作归档冗余。归档状态 Unknown/后端失联不授权新的破坏性 Release；已经 Offline 的访问保留可恢复任务并等待后端恢复，不能发布未验证内容。后端自身目录仍属于归档对象的权威事实，不构建源文件元数据镜像。

## 9. HA 与性能一起验收

| 故障注入 | 必须验证的结果 |
|---|---|
| 集批前/后杀 leader，未提交尾部被覆盖 | 相同请求 ID 对账；没有伪成功或重复元数据效果 |
| 提交后丢响应，或本地 apply 前杀进程 | 新 leader 恢复原始结果；已确认操作不丢失 |
| leader 与多数派隔离，之后恢复 | 少数派无新权威效果，重连后丢弃未提交状态，不出现双重发布 |
| 控制器 kill / SIGSTOP / 分区后接管 | 旧资格被隔离；已完成 Archive/Release/Recall 对账，未知阶段安全重做 |
| 执行器在复制/封存/回执间故障 | 不发布半成品；新尝试不受旧写入污染，逻辑效果不重复 |
| 读者/续约过程中换主，时钟误差和跳变 | 读取保护不被提前遗忘；过期或撤销授权受控，Release 安全 |
| Worker 在正常写入、Recall 准备/发布后故障 | 按声明的 W/RPO 修复或重召回，原 inode/generation 语义保持 |
| 归档节点或 catalog 故障、恢复 | 既有锚点可精确查询；新的 Release 不误用不确定回执 |
| 失去多数派后恢复；百万 namespace 有积压任务 | 不无限收队列；服务和任务分级恢复，不重新全盘扫描才能接管 |
| 旧数据目录/旧 checkpoint 节点重新加入 | 追齐健康多数派，不恢复过时资格或覆盖已提交结果 |

至少运行三个独立 Master 进程、独立控制器/执行器进程及真实 Worker 故障测试；节点/宿主机 HA 还须跨独立物理故障域。沿用百万 namespace 验证时记录其预置方式，不能把同进程 fixture kill 当作多节点故障矩阵。

记录：故障检测、选主、重放、Serving、控制器接管、首个访问 Recall/后台进度恢复的分段耗时，以及前台吞吐与 P95/P99、重复执行/发布计数。正常运行与故障窗口分别报告。RTO 是检测、接管、追齐/对账及必要数据恢复的总时间；Recall 的读等待预算（当前 300 秒）需与 HA 恢复和数据搬运时间共同验收，客户端超时不删除已入队任务。

发布门槛：P1/P2 的换主与幂等测试先于吞吐验收；自动控制器接管、后端数据/目录可用及 Recall 布局耐故障缺口关闭之前，不宣称端到端 HA。本文只更新设计，不将新增目标标记为已通过测试。
