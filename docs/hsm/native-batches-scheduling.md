# 批量写入与前后台调度

本页记录实际实现，不将历史吞吐数字作为本次优化收益。适用范围仍为无 UFS 的普通单链接文件；旧式 RPC 的投影隔离继续保留。

## 批量请求如何提交

`CreateFilesBatch`、`AddBlocksBatch` 和 `CompleteFilesBatch` 的 SDK 调用使用 NativeMutation。一个公开批量请求只有一个稳定 session/sequence 身份、一个持久结果，批内各项不单独创建会话。主协调器仍可把多个公开请求合为一个 proposal。

1. 在有界私有视图中按请求顺序准备各项。后项能看到前项创建的父目录、文件、块和写入状态，未提交内容对其他业务不可见。
2. 合并效果时保留每个 inode、目录项、HSM Record 的**第一次观察值**作为 CAS 条件，保存其最终状态。目录子项数量累加，位置与退休事实按键合并；退休事实只在最后构建一次映射，避免逐前缀反复合并的平方开销。
3. 一个公开请求原子发布一次，因此同一 Record 的内部多次变化合为一次版本推进；generation 和最终业务状态保留全部成功操作的效果。后续协调器命令看到合并后的版本。
4. inode、目录项、HSM Record、索引、退休事实、原始回复由一个 RocksDB WriteBatch 发布。Native journal v4 的已有 DTO 足以表达，不改变历史字段和编号。

| 批量接口 | 成功与错误行为 |
|---|---|
| 创建 | 顺序执行，遇错停止；成功前缀和原始错误一起提交，后续项不执行 |
| 块分配 | 同样遇错停止；成功前缀的 Worker 软调度预留保留，准备失败/已知拒绝时撤销，不确定时保守保留 |
| 文件关闭 | 保留每项 true/false，单项失败不阻止后项；失败项不安装私有效果 |

准备阶段总预算仍为 2 MiB；相邻请求收集最多 32 项、请求头预算 512 KiB，journal 总预算 8 MiB。公开批量头上限 2 MiB。预算错误也服从上述前缀/逐项语义，不承诺无限批量原子事务。

原始错误本身可以代表“已有成功前缀”，因此不能把 `success=false` 简单解释成无效果。提交前 CAS 冲突则整批不发布，并持久记录冲突结果；调用方不能用新身份重试不确定的旧请求。

## 为什么目录命令可以共享等待

rename、递归属性、递归删除和内部 TTL 删除只把紧凑输入写入 journal，直到 committed apply 才检查当前状态并展开子树，不会提前修改投影，也不在准备阶段分配 inode ID。因此它们与其他 owned 命令共享投影资格等待 Raft。

若准备之后出现新的读者，apply 会读取当前 Record，并使用已记录的保护时钟检查该读者；不能凭准备时没有读者就绕过保护。旧式先修改状态的 handler 和后台路径仍需独占资格。大目录展开的 O(N) 工作、FsDir apply 锁及写批内存没有被共享资格消除。

## 调度如何避免前后台互相挤占

`AuthorityGate` 保留共享/独占语义，按三个 FIFO 类别调度：Recall、前台、后台。持续有请求时，每轮分别分配 **4、8、1 个资格**，空类直接跳过。一个资格可能对应一个含多项逻辑请求的协调器批次；这些是轮次数量权重，不是带宽或墙钟时间保证。

- 三类各有 128 个名额，共享资格最多同时 32 个。HSM 控制入口也分别保留三类名额，后台请求不会占满 Recall 的接入容量。
- 普通读写、元数据查询及兼容 handler 属于前台；Prepare/Commit/AbortRecall 属于 Recall；策略筛查/入队、意图调度、Archive、Release、GC 属于后台。
- OS 后台独占修改属于后台；Native 队列内部另设前台/TTL 名额，持续前台请求最多执行 8 个协调器轮次就给等待 TTL 一次机会。
- 已选中的独占请求等待现有读者退出时，后来读者不能持续越过它。取消排队者立即移除，取消已授权者释放资格；已被 owned 任务接收的实际提交仍由任务完成或确认前缀。
- 控制操作等待 Worker 网络 I/O 时释放资格；回来后按原类别重新排队，并重新验证 ReadIndex、namespace 和 controller epoch。

调度仅改变本地等待顺序。Raft、CAS、租约、持久原始结果与未知结果的前缀隔离仍决定能否修改权威状态。文件级 HSM 控制与 Seal 已通过独立条件封装共享准备/等待，详见[文件级条件提交](conditional-controls.md)。策略修改/入队、任务 claim/finish 等跨记录控制及旧式路径仍保留独占等待。

`hsm_stage_duration` 的 `authority_queue` 操作及 `foreground/recall/background` 阶段标签记录排队时长；权重与限额目前是代码常量，没有新增运维配置。

## 外部 worker 的执行通道

常驻 hsm-rs worker 将 Recall 与 Archive/Release 分为两个执行通道，每类最多一个动作在执行。后台通道继续负责策略扫描和 Seal；Recall 通道单独轮询读触发的 Ready 工作。慢 Archive 不占用 Recall 的执行位置，连续 Recall 也不占用后台位置。`--once` 保留单次顺序执行语义；常驻模式的 `max-actions` 是每通道每轮的动作上限，报告新增 `lane` 字段。

`intent_list` 的 `ready_only=true` 可带 `work_class=recall|background`。Source 分别 seek 已有的 `work:0:` 和 `work:1:` 范围，每页最多 16 项，不逐页跳过另一类别的任务。未指定类别的旧查询行为保持；游标仍为不透明的 priority:id，跨类别游标返回 Invalid。没有增加索引格式或外部任务镜像。分类后的 Recall 列表查询也取得 Recall 调度资格。

客户端只持有一页工作，实际 claim、epoch 验证、原始结果和终态仍由 Curvine 维护。执行器收到跨类别数据时拒绝继续，需要使用匹配 Source 版本。当前为本地归档；这项改造没有实现共享磁带机的抢占调度。

## 验证边界

Master 回归覆盖批量同父目录、遇错停止与原始错误重试、重复关闭的版本归并、并发新读者导致全批 CAS 拒绝、加权最低进度、取消选中独占者、后台满额仍可接收 Recall、Native 前台/TTL 的轮次边界。

真实 TCP/Raft 用例执行 32 文件创建、块分配与含失败项的关闭；检查关闭后纳管、共享资格下 SDK rename 可进展、原始兼容 rename 被隔离。故障注入只针对指定 session，在真实 Raft commit/local apply 之后丢弃回执，要求请求返回 Uncertain；改名后使用相同身份重试必须返回原始前缀错误，不能重新创建旧路径。该 hook 仅在 `hsm-scale-test` 编译。

这不是网络分区、磁盘丢失或百万文件性能验收。进程重启及在线节点故障的最新结果另外记录在 hsm-rs 验证文档；最终吞吐对比仍需统一工作负载。


最终固定来源组合：Curvine Master 270 项及两个 TCP/Raft 用例通过；hsm-rs 固定 `222a3254` 的 32 项功能及全部文档测试通过。真实 CLI 的后台执行轮次暂停时，普通读取仍自动 Recall 并校验 1 MiB+37 字节；恢复后台后 Archive 完成。独立 Master 进程的两次在线选主、旧 Leader 恢复与结果不变也通过。日志和剩余边界见[优化方案](optimization-plan.md#执行通道组合验收代码-222a3254)。
